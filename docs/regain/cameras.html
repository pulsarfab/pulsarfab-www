Cameras & recovery

Keep capture failures contained and choose when regain may retry a download or take a replacement exposure.

Use PulsarFab regain Retryable Camera in NINA, a native ASCOM camera entry, or a camera slot on the Alpaca server. All three integrations share the Rust recovery engine. The imaging application waits during permitted recovery; exhausted recovery returns an error.

Start with the SDK

The ZWO SDK backend is the default and runs in an isolated Rust worker. Other ZWO models can use it when supported by the bundled SDK. Direct USB is experimental and still needs the ZWO Windows camera driver on Windows.

Default retry policy

ActionDefault
Download the same frame again2 retries, at any exposure length
Reconnect and take a replacement exposure3 retries, only for exposures ≤30 seconds
Wait before reconnecting5 seconds

These limits are configurable; a count of zero disables that retry type. The SDK can retry a download while it still reports a ready frame. Direct ASI2600, ASI6200, and ASI676 drivers can reread camera memory; the guide camera cannot reread the same frame.

A same-frame reread does not take another exposure, so it can recover a long integration even when the replacement-exposure limit is 30 seconds. A supervised SDK worker can be replaced if it hangs, preserving remembered settings without taking down the imaging application. Retained-frame recovery across worker replacement remains a research feature.

Restore cooling after reconnect

Regain restores camera settings and the cooler setpoint. Before taking another exposure, it waits for cooling to approach the temperature measured before the error and checks cooler output. Holding the restored setpoint for 30 seconds is also accepted.

Abort stops capture, then reconnects to restore controls and cooling without another exposure. A cleanup error after a successful download preserves the image and reconnects before the next capture.

Hardened USB transport and SDK-free capture

The experimental Direct USB backend never loads the camera SDK. It bounds each complete frame read, drains cancelled transfers before releasing buffers, rejects partial or late frames, and logs the failed chunk, completed byte count, and available USB status. Each retained-frame reread starts from byte zero with its own download timeout budget.

On Windows, the ASI2600MM Pro P25 can reopen its USB handle within the configured read-retry budget. It verifies the original camera identity and hashes of previously received pixel chunks, then rereads the retained frame without starting a new exposure. Missing verification evidence or a mismatch prevents this recovery from returning an image. Automatic USB port resets are not part of this path.

Windows Direct USB still needs the installed ZWO camera USB driver. Linux/macOS use native OS USB access; physical USB validation there remains incomplete. The SDK backend remains the default for broader model support. See model coverage and USB lifecycle evidence and precise recovery conditions.

SDK fallback and diagnostics

Fall back to SDK is a separate Direct USB option. It keeps the same camera and stays active until disconnect. It cannot repeat a failed long exposure unless the recapture limit permits it. Logs record retry reasons, fallback, cooler recovery, and final errors.

USB retry validation used controlled faults, not cable removal or power loss. See the recovery evidence and NINA validation for limits and tested behavior.
